# 论文复现工作区原型

问题：论文复现工作区应该把什么放在首屏主信息层级？

三个开发态方案通过 `?repro-prototype=a|b|c` 切换，均使用内存 mock 数据，不调用 API、不写数据库。原型只在 Vite 开发模式挂载，生产构建不会显示切换器。

## 方案

| 方案 | 结构 | 优点 | 取舍 |
| --- | --- | --- | --- |
| A | 左侧项目/章节树 + 中央 Markdown + 右侧大纲与实验摘要 | 最接近参考图的信息架构；章节跳转、正文和摘要同时可见 | 三栏在中窄屏需要收起右栏；编辑区横向空间较少 |
| B | 可折叠项目栏 + 专注编辑区 + 可开关检查器 | 写作/修订时空间最大；检查器按需出现；适合长文档 | 项目全貌和实验结果被放到检查器，跨章节扫描成本较高 |
| C | 项目列表主从布局 + 实验运行/附件/结果为首要层级 | 适合管理多个复现项目；实验状态、结果和附件可快速扫描 | Markdown 正文退到二级入口，不适合作为默认写作工作区 |

## 当前建议

建议选择 **方案 A** 作为第一版生产工作区：它同时验证了项目/章节导航、Markdown 编辑/预览/分屏、右侧大纲和实验摘要四个核心闭环，和用户提供的结构参考最接近，同时仍保留 Paper Study 的宣纸、墨色、朱砂和紧凑密度。方案 B 的“按需检查器”可作为中等宽度和移动端的折叠策略吸收；方案 C 的实验摘要和附件列表适合作为项目列表页或项目概览子视图，而不宜取代写作主界面。

这只是原型建议，生产实现必须等用户确认后开始；确认时应明确是否采用 A，或采用 A+B/C 的组合。

## 领域模型（实现前置说明）

- `ReproductionProject`：关联一篇库内 `Paper` 的用户复现项目；同一 `Paper` 可以有多个项目。
- `ReproductionDocument`：项目 Markdown 正文、revision 和保存状态；不复用 `SourceDocument`、`GeneratedArtifact` 或普通论文笔记。
- `ExperimentRun`：人工记录的实验运行，包含环境、命令、参数、数据版本、代码提交、随机种子、状态、时间、指标和结果摘要；第一版不执行任意 Shell。
- `ReproductionArtifact`：日志、图片、表格、模型输出等安全附件；不直接塞入 `GeneratedArtifact`。
- `ReproductionNote`：只有独立快速记录确有价值时才建立，不能与普通论文笔记混用。
- 论文删除不得静默级联删除复现资料。正式实现需要以迁移和 API 契约明确保留策略，至少保留复现项目、正文、运行、附件和笔记，并显式处理缺失的论文关联。
